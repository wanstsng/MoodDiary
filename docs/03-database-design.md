# Проектирование базы данных

## 1. Предметная область

Пользователь ведёт дневник: каждый день он создаёт **запись** — заголовок,
текст, дату события и настроение. Каждая запись относится к одной
**категории** (Личное, Работа, Здоровье) и может быть помечена любым
количеством **тегов** (отпуск, спорт, семья).

Отсюда две связи:

* **Один-ко-многим** — одна категория содержит много записей,
  но запись принадлежит ровно одной категории.
* **Многие-ко-многим** — у записи может быть много тегов,
  и один тег может стоять у многих записей. Такая связь не выражается
  внешним ключом напрямую, поэтому нужна промежуточная таблица `entry_tags`.

Итого **4 таблицы**: три основные и одна связующая — как требует ТЗ.

## 2. ER-диаграмма

```mermaid
erDiagram
    categories ||--o{ entries     : "содержит"
    entries    ||--o{ entry_tags  : "помечена"
    tags       ||--o{ entry_tags  : "используется в"

    categories {
        INTEGER id PK "автоинкремент"
        TEXT    name UK "уникальное имя категории"
        TEXT    color "цвет чипа #RRGGBB"
        TEXT    icon "имя ресурса иконки"
        INTEGER is_default "1 — предустановленная"
        INTEGER created_at "Unix-время, мс"
    }

    entries {
        INTEGER id PK "автоинкремент"
        TEXT    title "заголовок записи"
        TEXT    content "текст записи"
        INTEGER entry_date "дата события, мс"
        TEXT    mood "GREAT|GOOD|NEUTRAL|SAD|ANGRY"
        INTEGER category_id FK "-> categories.id"
        INTEGER is_favorite "признак избранного"
        INTEGER created_at "когда создана"
        INTEGER updated_at "когда изменена"
    }

    tags {
        INTEGER id PK "автоинкремент"
        TEXT    name UK "уникальное имя тега"
        TEXT    color "цвет чипа"
        INTEGER created_at "Unix-время, мс"
    }

    entry_tags {
        INTEGER entry_id PK_FK "-> entries.id"
        INTEGER tag_id   PK_FK "-> tags.id"
    }
```

Отдельно существует виртуальная таблица `entries_fts` — поисковый индекс над
`entries`. Она не хранит собственных данных и не является пятой сущностью
модели, а обслуживает изюминку проекта — полнотекстовый поиск.

## 3. Описание таблиц

### 3.1. `categories` — категории записей

| Поле | Тип | Ограничения | Назначение |
|------|-----|-------------|------------|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Первичный ключ |
| `name` | TEXT | NOT NULL, UNIQUE | Название категории |
| `color` | TEXT | NOT NULL, DEFAULT `#8B7CF6` | Цвет чипа в интерфейсе |
| `icon` | TEXT | NOT NULL | Имя drawable-ресурса |
| `is_default` | INTEGER | NOT NULL, DEFAULT 0 | Признак предустановленной категории |
| `created_at` | INTEGER | NOT NULL | Время создания, Unix-мс |

При первом запуске создаются три категории: «Личное», «Работа», «Здоровье».

### 3.2. `entries` — записи дневника

| Поле | Тип | Ограничения | Назначение |
|------|-----|-------------|------------|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Первичный ключ |
| `title` | TEXT | NOT NULL | Заголовок, обязателен при вводе |
| `content` | TEXT | NOT NULL, DEFAULT '' | Текст записи |
| `entry_date` | INTEGER | NOT NULL | Дата события, Unix-мс |
| `mood` | TEXT | NOT NULL | Настроение, значение перечисления |
| `category_id` | INTEGER | NOT NULL, FOREIGN KEY | Ссылка на категорию |
| `is_favorite` | INTEGER | NOT NULL, DEFAULT 0 | Избранная запись |
| `created_at` | INTEGER | NOT NULL | Время создания |
| `updated_at` | INTEGER | NOT NULL | Время последнего изменения |

Настроение хранится строкой, а в коде описано перечислением `Mood`:

| Значение | Подпись | Эмодзи |
|----------|---------|--------|
| `GREAT` | Отлично | 😄 |
| `GOOD` | Хорошо | 🙂 |
| `NEUTRAL` | Нейтрально | 😐 |
| `SAD` | Грустно | 🙁 |
| `ANGRY` | Злость | 😠 |

Строка вместо числа выбрана намеренно: если позже добавить или переставить
значения перечисления, уже сохранённые записи не «поменяют настроение»,
как случилось бы при хранении порядкового номера.

Разделение `entry_date` и `created_at` тоже осознанное: пользователь может
задним числом описать вчерашний день — тогда дата события вчерашняя, а время
создания сегодняшнее. Статистика активности строится по `entry_date`.

### 3.3. `tags` — теги

| Поле | Тип | Ограничения | Назначение |
|------|-----|-------------|------------|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Первичный ключ |
| `name` | TEXT | NOT NULL, UNIQUE | Название тега |
| `color` | TEXT | NOT NULL | Цвет чипа |
| `created_at` | INTEGER | NOT NULL | Время создания |

### 3.4. `entry_tags` — промежуточная таблица

| Поле | Тип | Ограничения | Назначение |
|------|-----|-------------|------------|
| `entry_id` | INTEGER | PRIMARY KEY (составной), FOREIGN KEY | Ссылка на запись |
| `tag_id` | INTEGER | PRIMARY KEY (составной), FOREIGN KEY | Ссылка на тег |

Составной первичный ключ `(entry_id, tag_id)` гарантирует, что один и тот же
тег нельзя повесить на запись дважды.

## 4. Внешние ключи и каскадное удаление

| Связь | Правило удаления | Смысл |
|-------|------------------|-------|
| `entries.category_id → categories.id` | `ON DELETE CASCADE` | Удаляя категорию, удаляем её записи — прямое требование ТЗ |
| `entry_tags.entry_id → entries.id` | `ON DELETE CASCADE` | Удалили запись — её связи с тегами исчезают |
| `entry_tags.tag_id → tags.id` | `ON DELETE CASCADE` | Удалили тег — он снимается со всех записей |

Важная деталь: SQLite **по умолчанию не проверяет внешние ключи**. Их нужно
включать директивой `PRAGMA foreign_keys = ON` для каждого соединения.
В приложении это делает Room (`AppDatabase.onOpen`), в проверочном скрипте —
явный вызов после применения схемы.

## 5. Индексы

| Индекс | Таблица и поля | Зачем нужен |
|--------|----------------|-------------|
| `index_categories_name` | `categories(name)` UNIQUE | Уникальность имени категории |
| `index_tags_name` | `tags(name)` UNIQUE | Уникальность имени тега |
| `index_entries_category_id` | `entries(category_id)` | Фильтр по категории и каскадное удаление без полного перебора таблицы |
| `index_entries_entry_date` | `entries(entry_date)` | Сортировка по дате и фильтр по периоду |
| `index_entries_mood` | `entries(mood)` | Фильтр по настроению |
| `index_entry_tags_tag_id` | `entry_tags(tag_id)` | Поиск записей по тегу (первая колонка составного ключа уже проиндексирована) |

## 6. Полнотекстовый поиск

```sql
CREATE VIRTUAL TABLE entries_fts USING fts4(
    title, content, content=`entries`, tokenize=unicode61
);
```

Параметр `content=entries` включает режим внешнего содержимого: виртуальная
таблица хранит только поисковый индекс, а тексты берёт из `entries`. Это вдвое
экономит место и исключает расхождение данных.

Синхронизацию обеспечивают четыре триггера (`AFTER INSERT`, `BEFORE UPDATE`,
`AFTER UPDATE`, `BEFORE DELETE`). Триггеры на изменение и удаление именно
`BEFORE`: строка в `entries` в этот момент ещё существует, и FTS может
корректно вычислить, какие слова убрать из индекса.

Поисковый запрос:

```sql
SELECT e.* FROM entries e
JOIN entries_fts f ON f.docid = e.id
WHERE entries_fts MATCH :query;
```

В сравнении с `LIKE '%слово%'` это принципиально другой механизм: `LIKE`
не может использовать индекс и всегда читает всю таблицу, а FTS обращается
к инвертированному индексу и находит совпадения за логарифмическое время.

### Почему токенизатор задан явно

Параметр `tokenize=unicode61` — не украшение. Токенизатор по умолчанию
(`simple`) приводит к нижнему регистру только латиницу. Из-за этого запись
«Парковка у дома» попадала бы в индекс со словом «Парковка» — с заглавной
буквой, — и запрос «парк» её бы не нашёл. Это выяснилось на проверке схемы:
из шести тестов поиска три провалились именно так. `unicode61` приводит
регистр по правилам Unicode, и все проверки проходят.

### Подготовка пользовательского ввода

Строку из поля поиска нельзя передавать в `MATCH` как есть: у FTS свой язык
запросов, где кавычки, скобки, дефис и слова `AND`, `OR`, `NEAR` имеют
особое значение. Ввод вроде `код -ошибки` или незакрытая кавычка вызвали бы
синтаксическую ошибку SQL — то есть падение поиска на совершенно обычном
для пользователя тексте.

Поэтому `SearchQueryBuilder` оставляет от ввода только слова и добавляет к
каждому `*`:

| Ввод пользователя | Запрос к FTS |
|-------------------|--------------|
| `парк` | `парк*` |
| `код -ошибки` | `код* ошибки*` |
| `парк"` | `парк*` |
| `(парк)` | `парк*` |
| `   ` | пустая строка — поиск отключён |

Пробел между словами в FTS означает «И», поэтому чем больше слов ввёл
пользователь, тем точнее результат. Звёздочка даёт поиск по началу слова:
«парк» находит и «парке», и «Парковка».

## 7. Основные запросы

| Задача | Запрос |
|--------|--------|
| Список записей с категорией | `SELECT ... FROM entries e JOIN categories c ON c.id = e.category_id ORDER BY e.entry_date DESC` |
| Теги одной записи | `SELECT t.* FROM tags t JOIN entry_tags et ON et.tag_id = t.id WHERE et.entry_id = :id` |
| Фильтр по настроению и категории | `WHERE (:mood IS NULL OR e.mood = :mood) AND (:categoryId IS NULL OR e.category_id = :categoryId)` |
| Всего записей | `SELECT COUNT(*) FROM entries` |
| Частое настроение | `SELECT mood, COUNT(*) c FROM entries GROUP BY mood ORDER BY c DESC LIMIT 1` |
| Распределение по категориям | `SELECT c.name, COUNT(e.id) FROM categories c JOIN entries e ON e.category_id = c.id GROUP BY c.id` |
| Активность за 7 дней | `SELECT entry_date FROM entries WHERE entry_date >= :weekStart` |

Все агрегаты считаются средствами SQL, а не перебором списка в памяти:
на экране статистики это разница между одним запросом и выгрузкой всех
записей в оперативную память.

## 8. Проверка схемы

Схема не просто описана на бумаге — она проверяется автоматически:

```bash
python3 tools/verify_schema.py
```

Скрипт создаёт базу в памяти, применяет `tools/schema.sql`, заполняет её
тестовыми данными и выполняет 31 проверку: наличие таблиц, объявление и
работу внешних ключей, обе связи, каскадное удаление, полнотекстовый поиск
(включая обновление индекса при `UPDATE` и `DELETE`) и запросы статистики.

одно слово не потеряно, записи не выходят за нижний край страницы.
